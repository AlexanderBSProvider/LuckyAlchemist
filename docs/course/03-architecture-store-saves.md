## 1. Теорія

### Навіщо взагалі шари

Без чіткого правила "хто кого імпортує" код природно скочується до стану, коли ігрова
математика (скільки золота дає варка) переплітається з кодом, що малює кнопку. Змінити
візуал стає страшно — раптом зламається розрахунок. Тестувати розрахунок стає незручно —
для тесту доводиться імітувати браузер. Шари з ARCHITECTURE.md §1 (`data → core → store →
{ui, render, audio, platform}`) — це правило одного напрямку `import`: нижній шар ніколи не
знає про верхній. `core/` можна повністю протестувати в Node без жодного браузера — саме
так і зроблено (`tests/core/`).

### Store: `getState` / `dispatch` / `subscribe` — і чому не Redux/Zustand

Патерн "єдиний об'єкт стану + єдина точка його зміни" не винайдений Redux'ом — це просто
зручний спосіб мати один достовірний "знімок" даних гри, за яким може стежити будь-яка
кількість підписників (UI, рендер, автозбереження), не боячись розсинхронізації. У проєкті
без React бібліотека на кшталт Zustand не дає нічого понад цей патерн, окрім синтаксичного
цукру — тому [src/store/store.ts](../../src/store/store.ts) реалізує його вручну, у
~50 рядків:

```ts
export function createStore<State>(initialState: State): Store<State> {
  let state = initialState;
  // ...
  const dispatch: Store<State>["dispatch"] = (command) => {
    state = command(state);
    // повідомити підписників, чиї селектори змінились
  };
}
```

Ключове рішення: **`state` ніколи не мутується**, тільки замінюється цілком новим об'єктом
(`command(state)` повертає новий стан, а не змінює старий). Це видно в
[src/store/commands.ts](../../src/store/commands.ts):

```ts
export function markSaved(now: number): Command<GameState> {
  return (state) => ({ ...state, lastSavedAt: now }); // новий об'єкт, старий не чіпаємо
}
```

`{ ...state, lastSavedAt: now }` — спред-оператор копіює всі поля `state`, потім
перезаписує одне. Чому це важливо: `store.subscribe` порівнює *попереднє* і *нове* значення
селектора через `Object.is`/пошарове порівняння
([src/store/shallow-equal.ts](../../src/store/shallow-equal.ts)) — якщо старий об'єкт
змінили на місці, порівняння "старе з новим" завжди показувало б "однаково" (це той самий
об'єкт!), і підписники ніколи б не спрацювали.

### `subscribe` із селектором: навіщо не просто "підпишись на все"

```ts
store.subscribe((state) => state.resources.gold, renderGold);
```

Компонент, якому потрібне лише золото, не повинен перемальовуватись, коли змінюється
`lastSavedAt`. `subscribe` зберігає останнє значення селектора і викликає `listener` тільки
якщо нове значення відрізняється (shallow-equal). Це мікроверсія того, що в React-світі
роблять "селектори" в Redux чи Zustand — тут написано руками, щоб було видно кожен крок.

### Event bus: стан проти подій

`store` відповідає на питання "яка зараз ситуація" (скільки золота **зараз**). Але
"зілля щойно вибухнуло" — це не стан, а **подія**: щось відбулось один раз і мента
пройшло. Саме для цього — [src/store/events.ts](../../src/store/events.ts):

```ts
export type GameEventMap = {
  "save:written": { at: number };
  "save:loaded": { at: number };
  "save:load-failed": { reason: string };
};
```

**Важливий нюанс TypeScript**, з яким ми зіткнулись буквально під час написання цього
файлу: `GameEventMap` — навмисно `type`, а не `interface`, попри те, що ESLint-правило
`consistent-type-definitions` за замовчуванням вимагає `interface` для об'єктних типів.
Причина в рядку нижче:

```ts
export interface EventBus<EventMap extends Record<string, unknown>> { ... }
```

`EventBus<GameEventMap>` компілюється, тільки якщо `GameEventMap` "підходить" під обмеження
`Record<string, unknown>` (довільний рядковий ключ → будь-яке значення). Об'єктні типи,
оголошені через `type X = {...}`, отримують **неявний індексний підпис** при такій
перевірці; `interface X {...}` — ніколи, через те що інтерфейси можна доповнювати новими
властивостями в іншому місці коду (declaration merging), і TypeScript не може гарантувати
наперед, що майбутнє доповнення не порушить `Record<string, unknown>`. Тому в
[src/store/events.ts](../../src/store/events.ts) стоїть явний коментар і
`eslint-disable-next-line` саме на цьому рядку — типова ситуація, коли два розумні правила
(TypeScript generic constraints і стиль ESLint) конфліктують, і рішення потрібно
задокументувати, а не мовчки обійти.

### Персистентність: чому вона не всередині `store/`... і водночас там

[src/store/persistence.ts](../../src/store/persistence.ts) містить `saveGame`/`loadGame` —
функції, що **роблять I/O** (записують у сховище). Хіба це не порушує правило "`store` не
залежить від `platform`"? Ні — і ось як:

```ts
export interface SaveIO {
  save: (raw: string) => Promise<void>;
  load: () => Promise<string | null>;
}
```

`persistence.ts` оголошує **власний, локальний** інтерфейс `SaveIO` — саме той мінімум,
який йому потрібен, — замість імпорту `PlatformAdapter` з `platform/types.ts`. Коли пізніше
в `main.ts` викликається `saveGame(store, platformAdapter, ...)`, TypeScript перевіряє не
"чи це офіційно `PlatformAdapter`", а "чи об'єкт має методи `save`/`load` з потрібними
сигнатурами" — це називається **структурна типізація** (structural typing), і саме вона
дозволяє `createLocalAdapter()` (який повертає повний `PlatformAdapter` із шістьма
методами) підійти туди, де очікується куций дволичковий `SaveIO`, без жодного явного
приведення типів чи спільного імпорту. Це конкретний приклад **інверсії залежностей**:
споживач (`store/persistence.ts`) оголошує контракт, який йому потрібен; постачальник
(`platform/local.ts`) просто випадково йому відповідає, нічого не знаючи про існування
`store/`.

### `Result`-тип проти винятків: дві різні категорії помилок

Порівняй дві функції з написаного коду:

```ts
// core/rng.ts — програмістська помилка: неправильний виклик, кидаємо одразу
if (min > max) throw new RangeError(`Rng.int: min (${min}) must be <= max (${max})`);
```

```ts
// core/save/serialize.ts — очікувана ситуація, повертаємо результат
export type DeserializeResult =
  | { ok: true; data: SaveDataV1 }
  | { ok: false; reason: "invalid-json" | "invalid-shape"; message: string };
```

Різниця не стилістична, а концептуальна. `min > max` в `Rng.int` — це помилка
**програміста**, що викликав функцію неправильно; такий код узагалі не повинен був
потрапити в продакшн, і виняток одразу зупиняє виконання, щоб баг не пройшов непоміченим.
Зіпсований `localStorage` (браузер впав під час запису, портал повернув пошкоджений
хмарний сейв) — це **очікувана, штатна** ситуація, яку викликач *зобов'язаний* обробити.
`deserializeSave` повертає `{ ok: false, reason, message }` замість того, щоб кидати
виняток — так TypeScript змушує (через типи `DeserializeResult`) перевірити обидві гілки
`if (result.ok)`, а не сподіватись, що хтось не забуде `try/catch`.

### Сейви й міграції: чому це не просто `JSON.stringify`

Гра, що живе роками (а idle-жанр саме такий), рано чи пізно змінить форму даних: додасть
інвентар, нову валюту. Старий сейв гравця, який не заходив місяць, має форму *попередньої*
версії. [src/core/save/migrations.ts](../../src/core/save/migrations.ts) розв'язує це
ланцюжком:

```ts
const migrations: Record<number, Migration> = {
  0: migrateV0ToV1,
  // 1: migrateV1ToV2,  ← так виглядатиме наступна міграція
};
```

`migrateToCurrent` визначає версію сирого сейву (`detectVersion`) і послідовно застосовує
міграції, поки не дійде до `CURRENT_SAVE_VERSION`. Кожна міграція відповідає лише за один
крок (`v0 → v1`), не за весь шлях одразу — так додавання `v2` ніколи не вимагає чіпати
логіку переходу `v0 → v1`, яка вже перевірена тестами й працює в проді.

`deserializeSave` пропускає результат через `saveDataV1Schema.safeParse(...)`
([src/core/save/schema.ts](../../src/core/save/schema.ts), Zod) — це кордон довіри:
навіть якщо міграція повернула щось неправильної форми (баг у самій міграції), Zod це
зловить, і гра стартує з чистого сейву, а не впаде з незрозумілою помилкою десь у бою.

### `main.ts` — композиційний корінь

[src/main.ts](../../src/main.ts) — єдине місце в проєкті, яке легально імпортує з усіх
шарів одразу (`core`, `store`, `platform`, `ui`). Це навмисний виняток із правила
"нижній шар не знає про верхній": хтось має зібрати всі шматки докупи, і краще, щоб це
робив один явний файл нагорі, ніж щоб залежності просочувались випадково по всьому коду.

## 2. Розбір коду

Пройди в такому порядку — це порядок реальної залежності одного від одного:

1. `src/core/save/schema.ts` → `factory.ts` → `migrations.ts` → `serialize.ts` — форма
   даних, потім як вона створюється, мігрує, серіалізується.
2. `src/store/game-state.ts` — зверни увагу: `GameState` це просто аліас `SaveDataV1`.
   Стан гри *дослівно* дорівнює тому, що зберігається — це не збіг, а свідоме рішення
   (ARCHITECTURE.md §7): "сейв — це знімок стану" тут не метафора.
3. `src/store/store.ts`, `commands.ts`, `events.ts` — сам store, чисті команди, канал подій.
4. `src/store/persistence.ts` — де все з'єднується: `SaveIO`, `saveGame`, `loadGame`.
5. `src/platform/types.ts`, `local.ts` — повний контракт порталу і найпростіша реалізація.
6. `src/main.ts` і `src/ui/app-shell.ts` — фінальне з'єднання: як `#app`-екран підписується
   на store й events, і що саме відбувається при кліку на "Зберегти".

Особливо придивись до тестів [tests/store/persistence.test.ts](../../tests/store/persistence.test.ts):
`createMemoryIO()` там — це самописний фейковий `SaveIO` (Map замість `localStorage`) —
працює лише завдяки структурній типізації, описаній вище.

## 4. Контрольні питання

1. Чому `dispatch` замінює весь об'єкт стану через spread (`{ ...state, x: y }`), а не
   змінює `state.x = y` напряму? Що конкретно зламалося б у `subscribe`?
2. У чому різниця між `interface` і `type` з погляду того, чи вони отримують "неявний
   індексний підпис" для перевірки generic-обмежень типу `Record<string, unknown>`?
3. Поясни структурну типізацію на прикладі `SaveIO`/`PlatformAdapter`: чому
   `createLocalAdapter()` можна передати туди, де очікується `SaveIO`, без явного каста?
4. Коли варто кидати виняток (`throw`), а коли повертати `{ ok: false, ... }`? Наведи по
   одному прикладу з написаного коду для кожного випадку, окрім тих, що вже в уроці.
5. Що станеться зі старим сейвом гравця, якщо в `CURRENT_SAVE_VERSION` збільшити версію,
   але забути зареєструвати відповідну міграцію в `migrations`?
