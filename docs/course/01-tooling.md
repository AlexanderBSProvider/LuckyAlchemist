## 1. Теорія

### Node.js і npm

Node.js — рушій JavaScript поза браузером; він виконує наші конфіги (`vite.config.ts`),
інструменти (`tools/econ-sim.ts`) і сам процес збірки. npm — менеджер пакетів, що йде в
комплекті з Node: він читає `package.json`, качає залежності в `node_modules/`, і генерує
`package-lock.json` — файл, що фіксує **точні** версії всього дерева залежностей, щоб
збірка була відтворюваною на іншій машині.

`package.json` має дві секції залежностей:
- `dependencies` — те, що потрапляє у фінальний бандл гри (у нас поки лише `zod`).
- `devDependencies` — інструменти розробки (Vite, TypeScript, Vitest, ESLint...), які
  ніколи не потрапляють у код, що завантажує гравець.

`scripts` у `package.json` — іменовані команди (`npm run dev`, `npm run test`). Це проста,
але важлива домовленість: будь-хто (людина чи CI) запускає одну й ту саму команду, не
пам'ятаючи довгих прапорців CLI.

### Vite: dev-сервер і бандлер

Vite вирішує дві різні задачі одним інструментом:
1. **Розробка** (`vite`/`npm run dev`) — dev-сервер, що віддає файли як є, компілюючи
   TypeScript "на льоту" через esbuild (дуже швидко), і оновлює сторінку без перезавантаження
   при зміні файлу (Hot Module Replacement).
2. **Продакшн-збірка** (`vite build`) — упаковує весь код у мінімальну кількість файлів
   (chunks), мінімізує їх, рахує хеші імен файлів для кешування браузером. Саме це кладе в
   `dist/` — те, що зрештою завантажує портал.

`vite.config.ts` у нас експортує `defineConfig({...})` з **`vitest/config`**, а не з `vite`
напряму — і це не випадковість. `vitest` (тестовий раннер) додає до конфіга Vite власну
секцію `test: {...}`; типи цієї секції існують тільки в обгортці `vitest/config`. Якщо
імпортувати `defineConfig` із голого `vite`, TypeScript не знатиме, що таке поле `test`, і
впаде з помилкою — так і сталось під час розробки цього етапу, і фікс саме такий.

### TypeScript: навіщо `strict` і що таке project references

TypeScript — надмножина JavaScript із системою типів, що перевіряється **до** запуску коду.
Мета — зловити цілий клас помилок (виклик неіснуючого методу, `undefined` там, де очікували
об'єкт) на етапі написання коду, а не в браузері гравця.

`strict: true` у `tsconfig.app.json` вмикає одразу пакет із ~8 суворих перевірок (типи
`null`/`undefined`, неявний `any` тощо). Ми пішли ще далі й додали окремі прапорці, кожен з
яких ловить конкретний реальний клас помилок:

| Прапорець | Що ловить |
|---|---|
| `noUncheckedIndexedAccess` | `array[i]` типізується як `T \| undefined`, а не `T` — бо індекс може вийти за межі |
| `exactOptionalPropertyTypes` | не дає плутати "властивості немає" з "властивість = `undefined`" |
| `noPropertyAccessFromIndexSignature` | змушує писати `obj["key"]` замість `obj.key`, коли `key` — динамічний, а не заявлена властивість |
| `noUnusedLocals`/`noUnusedParameters` | не дає лишити мертвий код |
| `verbatimModuleSyntax` | вимагає `import type`/`export type` для суто типових імпортів — швидша компіляція, чіткіший код |

**Project references** — це те, що `tsconfig.json` (кореневий) містить лише
`references: [...]` і жодних власних налаштувань. Ми розділили конфіг на два "проєкти":
`tsconfig.app.json` (код гри — `src/`, `tests/`, з `lib: DOM`) і `tsconfig.node.json`
(інструменти, що виконуються в Node, — `vite.config.ts`, `tools/`, з `lib: ES2022 + DOM`
для сумісності типів Vite). Причина розділення: код гри працює в браузері (є `window`,
`document`), а `vite.config.ts` виконується в Node (є `process`, немає `window` за
замовчуванням) — це різні середовища з різними глобальними об'єктами, і змішувати їхні типи
в одному конфізі означає або втратити помилки, або отримати хибні.

`npm run typecheck` виконує `tsc -b --noEmit` — `-b` означає "збери всі referenced-проєкти
в правильному порядку", `--noEmit` — "тільки перевір типи, не генеруй `.js`-файли" (це
робить Vite/esbuild, набагато швидше за `tsc`).

### ESLint (flat config) і Prettier: різні відповідальності

Це навмисно **два різні інструменти**, а не один:
- **Prettier** форматує (відступи, лапки, довжина рядка) — жодних думок про "правильність"
  коду, тільки про вигляд. Запускається як `npm run format`.
- **ESLint** шукає патерни, які працюють, але небезпечні або нестандартні (`no-unused-vars`,
  "цей `as`-каст насправді нічого не робить" тощо).

Якщо дати обом інструментам судити про форматування, вони конфліктуватимуть. Тому
`eslint.config.js` останнім пунктом підключає `eslint-config-prettier` — набір, що вимикає
в ESLint усі правила форматування, залишаючи Prettier єдиним джерелом істини про пробіли.

`eslint.config.js` — це **flat config**, сучасний формат ESLint (масив об'єктів-конфігів
замість старого `.eslintrc` з "extends"-ланцюжками). Кожен об'єкт у масиві — або глобальні
налаштування (`ignores`), або пресет (`js.configs.recommended`), або блок з `files` та
власними `rules`. У нас типізовані (type-aware) правила `typescript-eslint` застосовані
тільки до `files: ["**/*.ts"]` — не до самого `eslint.config.js` (він `.js`), бо type-aware
лінтинг вимагає реального `tsconfig`-проєкту для кожного файлу, а конфіг-файл сенсу
перевіряти на рівні типів немає.

**Чому `no-unnecessary-type-assertion` і подібні правила важливі для AI-коду:** коли код
пише LLM, найчастіша "стилістична" помилка — зайвий `as` там, де TypeScript і так вивів
потрібний тип. Це шум, що маскує місця, де каст справді необхідний і небезпечний.

### Git

`git init` створює порожній репозиторій; `.gitignore` каже Git ігнорувати `node_modules/`
(величезна, відтворювана з `package-lock.json`), `dist/` (згенерована збірка) — усе, що не
є вихідним кодом. Гілку за замовчуванням перейменовано на `main`, бо CI (`ci.yml`) очікує
саме цю назву в `on.push.branches`.

### CI (GitHub Actions)

`.github/workflows/ci.yml` описує послідовність кроків, що виконується на кожен push/PR:
`lint → format:check → typecheck → test → build → econ-sim`. Порядок навмисний — від
найшвидшої перевірки до найповільнішої: якщо код не проходить лінтер, немає сенсу чекати
на повільну збірку. Кожен крок — окрема npm-команда з `package.json`, тобто CI не робить
нічого, що ти не міг би запустити локально тими самими командами.

## 2. Розбір коду

Прочитай ці файли в такому порядку — саме так вони "розповідають" один сценарій:

1. [package.json](../../package.json) — які команди існують і які пакети підключені.
2. [tsconfig.json](../../tsconfig.json), [tsconfig.app.json](../../tsconfig.app.json),
   [tsconfig.node.json](../../tsconfig.node.json) — розділення на два проєкти, суворі
   прапорці з таблиці вище.
3. [vite.config.ts](../../vite.config.ts) — зверни увагу на імпорт з `vitest/config`, а
   не з `vite`.
4. [eslint.config.js](../../eslint.config.js) — блок `files: ["**/*.ts"]` з type-aware
   правилами, підключення `eslint-config-prettier` останнім.
5. [.github/workflows/ci.yml](../../.github/workflows/ci.yml) — послідовність кроків.

Зверни увагу на два коментарі-пояснення прямо в коді — це реальні пастки, у які ми
потрапили під час розробки цього етапу, і залишили пояснення на місці, а не в
git-історії, де їх ніхто не читає:

- `src/store/events.ts`, коментар над `GameEventMap` — чому там `type`, а не `interface`
  (детальніше — в уроці 03).
- `eslint.config.js`, коментар над `files: ["**/*.ts"]` — чому type-aware правила
  обмежені саме TypeScript-файлами.

## 3. Вправи

1. Заведи новий npm-скрипт `"check": "npm run lint && npm run typecheck && npm run test"`
   у `package.json` і переконайся, що він проходить локально.
2. Навмисно зроби помилку типів (наприклад, у будь-якому `.ts`-файлі присвой рядок змінній,
   типізованій як `number`) і запусти `npm run typecheck` — переконайся, що бачиш точне
   повідомлення про помилку з файлом і рядком.
3. Прибери `eslint-config-prettier` з кінця масиву в `eslint.config.js`, запусти
   `npm run lint`, подивись, чи з'явились конфлікти форматування, поверни файл назад.
4. Додай новий крок у `.github/workflows/ci.yml` (наприклад, `echo "custom step"`) і
   поясни собі, чому порядок кроків має значення (підказка: fail-fast).

## 4. Контрольні питання

1. Чим `dependencies` відрізняються від `devDependencies`, і чому `zod` — єдина реальна
   `dependency` в проєкті на цьому етапі?
2. Що саме ловить `noUncheckedIndexedAccess`, і чому саме він, а не звичайний `strict`,
   потрібен для безпечної роботи з масивами?
3. Чому в проєкті два `tsconfig`-файли (`app`/`node`), а не один спільний?
4. Чому Prettier і ESLint не повинні конфліктувати, і як саме `eslint-config-prettier` це
   гарантує?
5. Що станеться, якщо в CI поміняти місцями кроки `build` і `lint`? Чи зміниться
   *результат* пайплайна для явно зламаного лінтом коду? А *швидкість* зворотного зв'язку?
