# Архітектура

> Гейм-дизайн — у [GAME-DESIGN.md](GAME-DESIGN.md). Тут — як це побудовано технічно і
> чому саме так. Правила з цього документа обов'язкові для будь-якого коду, який
> потрапляє в проєкт (людина чи AI) — стисло вони продубльовані в [CLAUDE.md](../CLAUDE.md).

## 1. Шари і напрямок залежностей

```
        ┌─────────────┐
        │    data     │   JSON-конфіги балансу + Zod-схеми
        └──────┬──────┘
               │
        ┌──────▼──────┐
        │    core     │   чисті функції: варка, дистиляція, мутації, бій, економіка, сейви
        └──────┬──────┘
               │
        ┌──────▼──────┐
        │    store    │   стан гри + команди + event bus
        └──────┬──────┘
               │
   ┌───────────┼───────────┬───────────┐
┌──▼──┐    ┌───▼───┐    ┌──▼───┐    ┌───▼───┐
│ ui  │    │render │    │audio │    │platform│
└─────┘    └───────┘    └──────┘    └───────┘
```

Стрілки — це напрямок `import`. Він суворо один: нижній шар **ніколи** не імпортує
верхній. `core` не знає, що існує DOM чи Pixi. `store` не знає, що існує React-подібний
рендер чи звук. `ui`, `render`, `audio`, `platform` — листові шари, вони можуть імпортувати
`store` і `core`, але не імпортують одне одного (комунікація між ними — через store і
event bus, не напряму).

Чому саме так, а не «як зручніше по ходу»: `core` — єдине місце, де живе ігрова
математика. Якщо туди просочиться DOM або `Math.random()`, ми втрачаємо можливість
(а) юніт-тестувати формули ізольовано і (б) ганяти `tools/econ-sim.ts` — симуляцію тисяч
партій за секунди, без браузера. Це не естетика, а інструмент проти зламаного балансу.

## 2. `core/` — чиста логіка

Правила:
- Жодного `Math.random()` — тільки `Rng`, переданий явно як аргумент (`src/core/rng.ts`).
- Жодного `Date.now()`/`setTimeout` напряму — час приходить як параметр, де це потрібно.
- Жодних імпортів з `ui/`, `render/`, `audio/`, `platform/`.
- Кожна функція — детермінована: однакові аргументи (включно з станом Rng) → однаковий
  результат. Це дає відтворюваність (тижневі сід-челенджі, дебаг багрепортів, econ-sim).

Модулі (наповнюються поетапно за ROADMAP.md):
- `rng.ts` — seeded PRNG (sfc32) + допоміжні розподіли (`int`, `pick` за вагами, `fork`).
- `save/` — схема сейву, версіонування, міграції, серіалізація.
- `brewing/` — Етап 1: кільця, ваги символів, дека інгредієнтів.
- `distill.ts` — Етап 1: push-your-luck ґрейди.
- `mutations.ts` — Етап 1: слоти, теги, сет-ефекти.
- `battle.ts` — Етап 1: автобатлер-симуляція.
- `economy.ts` — Етап 1: ресурси, ціни, апгрейди.
- `progression.ts` — Етап 3+: епохи, свічі правил, престиж.

## 3. `data/` — баланс без коду

Кожен JSON-файл у `src/data/` має відповідну Zod-схему в `src/data/schemas.ts`. Схема —
кордон довіри: усе, що проходить `schema.parse(json)` під час білда/тестів, типізовано і
гарантовано валідне для решти коду. Це означає:

- Дизайнер балансу (тобто ти) редагує числа в JSON, не чіпаючи TypeScript.
- Помилка балансу (від'ємна вага, дірка в таблиці стейджів) ловиться Zod-помилкою в
  тестах/CI, а не рантайм-падінням у грі.
- AI, що пише код, ніколи не «зашиває» число в `core/` — тільки читає з `data/`.

## 4. `store/` — стан і команди

Замість Redux/Zustand — маленький типізований store власного письма
(`src/store/store.ts`, орієнтовно ~80–120 рядків):

```ts
const store = createStore(initialState);
store.getState();                          // поточний знімок
store.dispatch(command);                    // єдина точка мутації
store.subscribe(selector, callback);         // підписка з shallow-порівнянням
```

Чому не бібліотека: у проєкті без React немає сенсу тягнути Zustand заради синтаксичного
цукру — сам патерн (immutable snapshot + dispatch + subscribe) вивчається краще, коли
написаний руками і видно кожен рядок. Якщо колись знадобиться складніша реактивність —
замінити цей модуль на бібліотеку можна без зміни викликів `dispatch`/`subscribe` в іншому
коді (це і є мета інтерфейсу-кордону).

**Event bus** (`src/store/events.ts`) — окремий канал для *подій*, на відміну від *стану*.
Стан — «яка зараз ситуація» (скільки золота, який рівень лабораторії). Подія — «щось щойно
відбулось» (`brew:success`, `distill:burst`, `mutation:acquired`). UI/render/audio
підписуються на події для одноразових реакцій (анімація, звук), не перевіряючи стан щокадру.

## 5. `platform/` — портали без власного бекенду

```ts
interface PlatformAdapter {
  initSDK(): Promise<void>;
  gameplayStart(): void;
  gameplayStop(): void;
  showRewardedAd(): Promise<boolean>;
  save(data: string): Promise<void>;
  load(): Promise<string | null>;
}
```

`LocalAdapter` (localStorage, no-op реклама) існує з Етапу 0 — гра завжди грається локально
без порталу. `PokiAdapter`/`CrazyGamesAdapter` (Етап 4) реалізують той самий інтерфейс поверх
чужого SDK. Решта коду (`store`, `ui`) залежить тільки від інтерфейсу `PlatformAdapter`,
ніколи від конкретного SDK — заміна порталу не чіпає гру.

## 6. `render/` (PixiJS) і `ui/` (DOM)

- `render/` — усе, що малюється на Pixi-канвасі: казан, кільця символів, частинки,
  бойова сцена. Pixi-сцена читає `store`, підписується на événements для ефектів; вона не
  містить ігрової логіки (та логіка — в `core`, викликана через `store.dispatch`).
- `ui/` — DOM-шар (меню, інвентар, журнал, дерево апгрейдів): легкі функції-компоненти
  виду `(props) => HTMLElement`, що підписуються на store і прибирають за собою
  (`cleanup()` знімає слухачів). Без фреймворка — компонентна модель через прості функції
  й замикання, детально розібрано в курсі, модуль 3.

## 7. Сейви

Сейв = серіалізований знімок `store`-стану + номер версії схеми. При завантаженні:
`rawJson → validate → migrate(fromVersion → currentVersion) → hydrate store`. Реєстр
міграцій (`src/core/save/migrations.ts`) — це мапа `{ [fromVersion]: (old) => newer }`,
що застосовується послідовно. Пошкоджений/невалідний сейв → лог помилки + чистий старт,
гра ніколи не падає через зіпсований localStorage.

## 8. Тестування

- **Vitest** для `core/` і `store/` — щоденна робота, дзеркалить структуру `src/` у `tests/`.
- **`tools/econ-sim.ts`** — не unit-тест, а масовий прогін (тисячі симульованих сесій) на
  тому ж `core/`-коді; звіт по метриці «% застряглих гравців» іде в CI з Етапу 1.
- **Playwright smoke** (пізніше) — «гра відкривається, перша варка проходить» на реальному
  білді, ловить інтеграційні регресії, яких юніт-тести не бачать.

## 9. Бюджет і продуктивність

Початкове завантаження ≤ 5 МБ (вимога порталів). Наслідки для коду: активи епохи 2+
завантажуються ліниво (`import()`), Pixi-текстури — атласами, звук через Howler з
компресованими форматами. Деталі бюджету і вимірювання — в ROADMAP.md по кожному етапу.
