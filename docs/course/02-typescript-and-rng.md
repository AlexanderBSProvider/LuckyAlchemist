# Урок 02 — TypeScript у бою: чисті функції та seeded PRNG

> Модуль 1. Прив'язка: Етап 0. Код цього уроку: [src/core/rng.ts](../../src/core/rng.ts),
> тести: [tests/core/rng.test.ts](../../tests/core/rng.test.ts).

## 1. Теорія

### Типи як контракт, а не як документація

У слабо типізованих мовах коментар "приймає число від 1 до 6" — це обіцянка, яку ніхто не
перевіряє. У TypeScript сигнатура функції — це контракт, який **компілятор** перевіряє на
кожному виклику. Подивись на це:

```ts
export interface Rng {
  next: () => number;
  int: (min: number, max: number) => number;
  chance: (probability: number) => boolean;
  pick: <T>(entries: readonly WeightedEntry<T>[]) => T;
  fork: (label: string) => Rng;
}
```

Це не просто "чотири методи". Це заявляє: `int` завжди повертає `number` (не
`number | undefined`, не `any`) — і якщо десь у коді спробувати використати результат як
рядок, компілятор зупинить це до запуску гри. `pick<T>` — узагальнена (generic) функція:
вона працює з масивом будь-якого типу `T` і **гарантує**, що поверне значення саме цього
типу, а не якогось абстрактного "щось". Коли пізніше `core/brewing/` викличе
`rng.pick(ingredientEntries)`, TypeScript сам виведе, що результат — `Ingredient`, без
жодної ручної анотації.

### Чисті функції: чому це не просто стиль

Функція **чиста**, якщо для однакових вхідних аргументів вона завжди повертає однаковий
результат і не змінює нічого поза собою (жодних глобальних змінних, жодного запису у файл
чи DOM). `core/rng.ts` — приклад чистоти в дії: жоден метод не звертається до
`Math.random()`, `Date.now()` чи будь-чого "зовнішнього". Уся "випадковість" насправді є
детермінованою функцією від переданого сіда.

Чому це критично саме для гри з азартною механікою:
1. **Тестованість.** Можна написати тест "з сідом X варка дає Y" і він ніколи не стане
   "flaky" (то проходить, то ні) — на відміну від тесту, що покладається на справжній
   рандом.
2. **`tools/econ-sim.ts` (Етап 1).** Щоб прогнати 10 000 варок за секунди й порахувати
   баланс, потрібна чиста, швидка функція без побічних ефектів — I/O чи `Math.random()`
   з його внутрішнім прихованим станом це б заблокували чи сповільнили.
3. **Тижневі сід-челенджі** (GAME-DESIGN.md, розділ 3) — усі гравці отримують той самий
   сід і теоретично можуть отримати той самий результат. Це неможливо без детермінізму.
4. **Відтворюваність багів.** Якщо гравець повідомляє "варка дала дивний результат", маючи
   сід і номер варки, можна відтворити точно ту саму послідовність локально.

### Як влаштований seeded PRNG: xmur3 + sfc32

PRNG (pseudo-random number generator) — це, по суті, функція `next(): number`, що на
кожному виклику повертає "випадкове на вигляд" число, але насправді детерміновано залежить
від внутрішнього стану, який змінюється щоразу.

Ми використовуємо зв'язку двох маленьких, добре відомих алгоритмів (не з бібліотеки — щоб
не тягнути залежність заради ~60 рядків коду, і щоб було що показати в цьому уроці):

- **`xmur3(seed: string)`** перетворює довільний рядок (наш сід, наприклад ID сесії
  гравця) на потік добре "перемішаних" 32-бітних чисел. Рядок сам по собі — погане джерело
  випадковості (сусідні символи дають схожі байти); `xmur3` виправляє це бітовими зсувами й
  множенням.
- **`sfc32(a, b, c, d)`** бере чотири 32-бітних числа (стан) і на кожному виклику повертає
  наступне псевдовипадкове число, оновлюючи внутрішній стан. Це швидкий, компактний
  алгоритм — не криптографічно стійкий (для гри це не потрібно), але зі статистично
  добрими властивостями.

`createRng(seed)` з'єднує їх: бере чотири числа з потоку `xmur3(seed)` і використовує їх як
початковий стан `sfc32`. Результат — функція `next()`, що детерміновано залежить лише від
`seed`.

### Від `next()` до ігрових примітивів

`next()` повертає число в `[0, 1)` — незручно для гри напряму. Три похідні функції
перетворюють його на те, що реально потрібно:

- **`int(min, max)`** — ціле число в діапазоні (включно з обома кінцями): множимо
  `next()` на розмір діапазону й округлюємо вниз.
- **`chance(probability)`** — булеве "пощастило чи ні": `next() < probability`.
- **`pick(entries)`** — зважений вибір одного значення з декількох (саме так символи
  на кільцях казана матимуть різну рідкість): "розкручуємо" `next() * totalWeight` і йдемо
  по списку, віднімаючи вагу кожного елемента, поки не "потрапимо" в потрібний.

### `fork`: незалежні, але детерміновані підпотоки

Уяви, що варка й бій обидва потребують випадковості в той самий момент. Якщо вони
використовуватимуть той самий `Rng`, порядок їхніх викликів (варка спершу чи бій) впливав
би на результат іншого — крихка залежність. `fork(label)` вирішує це: витягує одне число з
батьківського потоку (тому й "коштує" йому один виклик `next()`) і на основі цього числа
плюс `label` створює **новий, незалежний** `Rng` через той самий `createRng`. Той самий
батьківський стан + той самий `label` завжди дають той самий дочірній потік — детермінізм
зберігається на кожному рівні.

### Vitest: `describe`/`it`/`expect`

Vitest групує тести в `describe` (логічний блок, наприклад "усе про `pick`") і `it`
(один сценарій, "ignores zero-weight entries"). `expect(value).toBe(x)` — точна рівність;
`toThrow(RangeError)` — очікування, що функція кине виняток конкретного типу;
`toBeGreaterThan`/`toBeLessThan` — для статистичних перевірок, де точне число непередбачуване,
але діапазон — так.

## 2. Розбір коду

Відкрий [src/core/rng.ts](../../src/core/rng.ts) поруч із
[tests/core/rng.test.ts](../../tests/core/rng.test.ts) і пройди відповідність:

- `xmur3`/`sfc32` (рядки з коментарем "Algorithm:") ↔ тести `describe("createRng")` на
  детермінізм: однаковий сід → однакова послідовність `next()`.
- `int` ↔ `describe("int")`: перевір, що тест "can return both endpoints given enough
  draws" саме тому робить 500 прогонів, а не один — статистична, а не точна перевірка.
- `pick` ↔ `describe("pick")`: тест `respects relative weights over many draws` доводить,
  що вага 1 проти ваги 3 дає приблизно 25%/75%, а не рівно.
- `fork` ↔ `describe("fork")`: чотири тести доводять чотири окремі властивості —
  детермінізм, незалежність від батька, залежність від `label`, і те, що батько
  просувається рівно на один виклик. Кожна властивість — окремий тест, а не один великий
  `it`, щоб при падінні одразу було зрозуміло, **що саме** зламалось.

Зверни увагу на обробку помилок: `int` кидає `RangeError`, якщо `min > max`; `pick` кидає
`RangeError` на порожньому списку чи нульовій сумі ваг. Це **програмістські помилки**
(неправильний виклик функції), тому вони кидають виняток одразу — на відміну від
`deserializeSave` в уроці 03, де невалідний ввід — очікувана ситуація, оброблена без
винятків.

## 3. Вправи

1. Додай метод `Rng.bool(): boolean` (50/50, без параметра) і напиши для нього тест.
2. Напиши тест, що доводить: `createRng("a").fork("x").next()` НЕ дорівнює
   `createRng("a").fork("y").next()` для трьох різних пар лейблів (уже є один такий тест —
   зроби його параметризованим через `it.each`).
3. Навмисно зламай `pick`: приший `>` замість `<` у порівнянні `roll < entry.weight` і
   подивись, які саме тести з `rng.test.ts` почервоніють. Це покаже, наскільки тести
   локалізують місце помилки.
4. Виміряй швидкість: скільки викликів `createRng("x").next()` можна зробити за секунду?
   (Підказка: знадобиться в Етапі 1 для econ-sim на 10 000+ варок.)

## 4. Контрольні питання

1. Чому `Rng` — це `interface` з методами-полями (`next: () => number`), а не клас із
   `Math.random()` всередині?
2. Що станеться з детермінізмом гри, якщо `int` замість `next()` раптом викличе
   `Math.random()` "про всяк випадок" для більшої "випадковості"?
3. Чому `pick` перебирає елементи по черзі, віднімаючи вагу, а не ділить одразу на
   `totalWeight` і порівнює індекс?
4. У чому конкретна різниця (в термінах стану) між `rng.next()` двічі поспіль і
   `rng.fork("a").next()` та `rng.fork("b").next()`?
5. Чому тест на розподіл `pick` (`heads`/`tails`) перевіряє діапазон `[0.2, 0.3]`
   замість рівно `0.25`, і що станеться, якщо звузити цей діапазон до `[0.24, 0.26]`?
